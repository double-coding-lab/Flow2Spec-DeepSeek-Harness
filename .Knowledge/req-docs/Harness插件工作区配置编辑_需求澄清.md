# Harness 插件工作区配置编辑 需求澄清

## 背景与目标

`flow2spec.config.json` 是**项目级**文件：同一台机器上每个仓库一份，`subAgent`、`changeTracking`、`collaboration.developerId` 各不相同。目前改它只能打开仓库手工编辑 JSON，改错一个键就要等下次跑技能时才发现。

Harness 的「设置 → 插件配置」卡片挂在 profile 上，本身没有「当前项目」这个概念——设置页不挂在任何一场对话上。因此卡片要做配置编辑，正确形态是**先让用户选工作区，再编辑该工作区的配置**：把作用范围摆在界面上，而不是靠一个隐含的 cwd 猜。

本需求给卡片加两件事：按工作区选择并编辑 `flow2spec.config.json`；对尚未初始化的工作区提供初始化入口。

### 与既有澄清文档的关系

`Harness插件设置卡片_需求澄清.md` 的「不包含」中有两条被本需求**显式推翻**：

| 原决定 | 现决定 | 推翻理由 |
|---|---|---|
| 不在卡片上编辑 `flow2spec.config.json` | 按工作区编辑 | 原决定假设卡片是 profile 级只读面板，无法承载项目级配置；引入工作区选择器后该前提消失 |
| 不在卡片上执行项目初始化 | 提供初始化按钮（带二次确认） | 工作区列表里必然混有未初始化的仓库，只标注状态而不给出口，用户还是得回命令行 |

其余「不包含」条目继续有效，尤其是：不把 Cordis `Config` 映射成卡片开关、不在卡片内执行插件安装或 Core 升级、不另做独立 Web 管理页。

## 范围

### 包含

- 卡片顶部保留现有全局信息：插件版本、Core 版本、「检查更新」按钮。版本与工作区无关，位置不变。
- 版本区下方新增工作区区：
  - 工作区来源为**宿主已注册列表**（`settings.plugin.item` 插槽标准 prop `useWorkspaces`，即侧边栏可见的那些），不扫盘、不手填路径。
  - 交互为**先选一个工作区**，下方只显示该工作区的配置；列表长时提供搜索过滤。
- 已初始化的工作区：以**结构化表单**编辑 `flow2spec.config.json` 全部字段。
- 未初始化的工作区：显示「未初始化」，提供**初始化**按钮；点击后先列出将要写入的内容，用户确认后才执行。
- 保存为**显式动作**：改动先留在卡片内，点「保存」才写盘；保存前可放弃。
- 保存**检测外部改动**：文件在卡片加载后被编辑器或 Agent 改过时，拒绝保存并提示重新加载。
- 写回**保留未知字段**：只覆盖表单改动过的键，文件里我们不认识的字段原样留下。
- 修改 `collaboration.developerId` 时提示：已有的 `.task/<旧 id>/` 目录不会跟着改名。

### 不包含

- 不提供原始 JSON 文本框（表单是唯一编辑入口）。
- 不在本次补 `/flow2spec config` 子命令；TUI 与命令行下改配置仍走手工编辑文件。
- 不做工作区注册、重命名、删除（那是宿主侧边栏的职责）。
- 不做配置的跨工作区复制、模板、批量应用。
- 不做配置变更历史、回滚、diff 预览。
- 不因卡片上的改动去重启会话或重载已在跑的 Agent。
- 不改变 `/flow2spec` 既有子命令与模型工具行为。

## 关键流程

### 选择工作区

1. 用户打开「设置 → 插件配置」，看到 Flow2Spec 卡片：顶部版本区，下方工作区区。
2. 工作区区列出宿主已注册的工作区，每项显示 `title` 与 `path`。
3. 用户选中一个工作区；卡片向宿主侧请求该路径的配置。
4. 结果分两种：
   - 该工作区已有 `flow2spec.config.json`：渲染配置表单；
   - 没有：显示「未初始化」与初始化按钮。

### 编辑并保存

1. 用户在表单上改动若干字段；卡片标记为「有未保存改动」，「保存」按钮可用。
2. 用户点「保存」。
3. 宿主侧重新读取磁盘上的文件，与卡片加载时记录的内容指纹比对：
   - **一致**：把改动过的键写进解析后的对象（未知字段原样保留），序列化写回，卡片回到已保存态；
   - **不一致**：拒绝写入，提示文件已被外部修改，请重新加载；用户重新加载后改动丢失，这是有意的取舍——不猜测两边该以谁为准。
4. 写入失败（路径消失、无写权限等）时保留用户改动，显示失败原因，允许重试。

### 初始化未初始化的工作区

1. 用户在未初始化的工作区上点「初始化」。
2. 卡片列出将要写入的内容（`flow2spec.config.json`、`.Knowledge/`、`.dsh/` 等），等待确认。
3. 用户确认后，宿主侧执行与 `/flow2spec init` 相同的调用：`project.api.project.init({ mode: 'native-host', locale })`。
4. 成功后刷新该工作区状态，直接渲染出配置表单。
5. 失败时显示原因，工作区保持未初始化。

## 边界与异常

- 宿主未注册任何工作区时，工作区区显示空态说明（去侧边栏添加工作区），版本区照常可用。
- 卡片打开期间宿主工作区列表发生变化（新增/删除）时，列表跟随更新；当前选中项被删除则回到未选中态。
- 同一份配置文件可能被多个 Harness 标签页同时打开：靠保存时的指纹比对兜底，后保存的一方会被拒绝而不是静默覆盖。
- 表单不接受非法值：布尔字段只有开关，`locale` 为受限选项，`developerId` 为文本但按 Flow2Spec 的 sanitize 口径校验（小写、非 `[a-z0-9]` 收成 `-`、长度 1–64），不合规时阻止保存并就地提示。
- `developerId` 留空是合法值，含义是回退到 git 邮箱/用户名推断，需在表单上写明，避免用户以为「空 = 坏了」。
- 配置改动对已在运行的会话不追溯生效；表单上说明「下次技能执行时生效」，不承诺热更新。
- 初始化按钮只对未初始化工作区出现；已初始化的工作区不提供「重新初始化」。
- 文案中英双份，跟随 Harness 界面语言（locale key 用 `zh` / `en`）。

## 关键概念定义

| 概念 | 定义 |
|---|---|
| 工作区 | 宿主注册表里的一条记录，含 `workspaceId`、`path`（规范化目录）、`title`。卡片通过插槽标准 prop `useWorkspaces` 读取，不自行维护列表。 |
| 已初始化 | 该工作区目录下存在 `flow2spec.config.json`。这是本需求判定「能否编辑配置」的唯一依据。 |
| 内容指纹 | 卡片加载配置时由宿主侧计算并下发的一个值，保存时用于判断磁盘文件是否被外部改过。 |
| 未知字段 | 磁盘文件中存在、但不属于当前表单已知字段集的键。写回时原样保留。 |
| 表单已知字段 | `locale`、`subAgent`、`switchAgentVerification`、`intentRecognition`、`changeTracking.feat` / `.fix` / `.implement`、`updateCheck.enabled`、`collaboration.enabled` / `.developerId`。 |

## 验收标准

- 卡片顶部仍显示插件版本、Core 版本与「检查更新」，行为与本需求实施前一致。
- 卡片下方能列出宿主已注册的全部工作区，可搜索、可选中；选中后只显示该工作区的配置。
- 选中一个已初始化的工作区，表单能正确回显该仓库 `flow2spec.config.json` 的实际取值；换选另一个工作区，回显随之切换。
- 改动字段后「保存」可用，点击后磁盘文件确实变更，且文件中原有的未知字段仍在。
- 在卡片打开的状态下用编辑器改动同一文件，再点「保存」，卡片拒绝写入并提示重新加载，磁盘上的外部改动未被覆盖。
- 修改 `developerId` 时能看到关于 `.task/<旧 id>/` 不会改名的提示。
- 选中未初始化的工作区时看到「未初始化」与初始化按钮；点击后先看到将写入内容的确认，确认后目录下生成 `flow2spec.config.json` 与 `.Knowledge/`，卡片随即显示配置表单。
- 没有任何注册工作区时卡片可正常打开，显示空态而不报错。
- `/flow2spec` 各子命令与模型工具行为不被本需求改坏。
